# Worked example: synthetic Login screen → EARS

This example shows the M3 pipeline output without touching any private
design. The input is a synthetic node list that mimics what `figma_get_file`
returns at `depth=3` for a generic login screen.

Reproduce with:

```
npm run verify:ears
```

## Input (synthetic Figma node tree)

```
Document
└── Login Page  (CANVAS)
    └── Login Form  (FRAME)
        ├── Email                       (INPUT)
        ├── Password                    (INPUT)
        ├── Remember me                 (INSTANCE)
        ├── Sign in                     (INSTANCE)
        ├── Forgot password?            (TEXT)
        └── Error: invalid credentials  (TEXT)
```

## Output (Ollama gemma3:4b, temperature 0.1)

The LLM returns strict JSON; the extractor parses it into typed
`EarsRequirement[]`. Below is a representative run — exact wording varies
slightly between runs because the model is non-deterministic even at low
temperature.

| ID | Pattern | Requirement | Source nodes |
|----|---------|------------|--------------|
| R1 | event | When the user clicks the Sign in button, the system shall submit the login credentials. | `2:4` / Sign in |
| R2 | event | When the user enters invalid credentials, the system shall display the Error: invalid credentials text. | `2:6` / Error: invalid credentials |
| R3 | event | When the user clicks the Forgot password? link, the system shall display the Forgot password? text. | `2:5` / Forgot password? |

Every requirement starts with one of the five EARS keywords
(`The | When | While | Where | If`), which is what the M4 lint pass
checks deterministically.

## Lint pass (M4)

After extraction, `npm run verify:ears` immediately runs the 6-rule lint
engine over the LLM output. A clean run on the synthetic login screen:

```
Lint: 3 checked, 3 clean, 0 error(s), 0 warning(s)

PASS: M3+M4 EARS extraction + lint round-trip via Ollama
```

The six rules ([ADR-0005](../adr/0005-lint-rule-selection.md)) catch:

- `R-001 EARS-KEYWORD` — text not starting with `The/When/While/Where/If`
- `R-002 EARS-PATTERN-MATCH` — pattern field mismatched with leading keyword
- `R-003 EARS-SHALL-PRESENT` — missing the modal verb `shall`
- `R-004 EARS-NO-AMBIGUITY` — hedge / vague terms in EN + JP
- `R-005 EARS-SOURCE-TRACEABLE` — empty source array (no Figma node to trace back)
- `R-006 EARS-SINGLE-ACTION` — more than one `shall` per requirement

A FAILED example, demonstrating the engine on a deliberately bad spec:

```
Lint: 3 checked, 1 clean, 3 error(s), 1 warning(s)
  ERR  [R-001 EARS-KEYWORD] R2: Text does not start with an EARS keyword (got: Should submit when clicked.).
  ERR  [R-003 EARS-SHALL-PRESENT] R2: Missing 'shall' (found: Should submit when clicked.).
  ERR  [R-002 EARS-PATTERN-MATCH] R2: Pattern 'event' implies keyword 'When' but text starts with: Should submit when clicked.
  WARN [R-005 EARS-SOURCE-TRACEABLE] R3: No source nodes referenced; requirement cannot be traced back to the design.
```

## Test generation (M5)

The `generate_tests` MCP tool (or `npm run demo`) turns the same spec
into a vitest file. One `it()` per requirement, grouped by source node,
each throwing `TODO` until a human fills it in:

```typescript
// AUTOGENERATED by figspec-pilot M5 (test-gen.ts).
// One it() per EARS requirement. Tests throw 'TODO' until filled in.
import { describe, it } from "vitest";

describe("Synthetic Login Screen", () => {
  describe("Sign in", () => {
    it("[R1] When the user clicks the Sign in button, the system shall submit the login credentials.", () => {
      // pattern: event
      // source: 2:4/Sign in
      // arrange:
      // act:
      // assert:
      throw new Error("TODO: implement test for R1");
    });
  });

  describe("Error: invalid credentials", () => {
    it("[R2] When the user enters invalid credentials, the system shall display the Error: invalid credentials text.", () => {
      // pattern: event
      // source: 2:6/Error: invalid credentials
      // arrange:
      // act:
      // assert:
      throw new Error("TODO: implement test for R2");
    });
  });

  // ... R3 ...
});
```

Why TODO-throwing? A passing auto-generated test would be a lie; making
each one fail loudly preserves the spec ↔ test linkage. See
[ADR-0006](../adr/0006-test-framework.md) for the framework rationale.

## End-to-end one-liner

```
npm run demo
```

The synthetic Login screen runs in ~30 s on a consumer laptop CPU
(`gemma3:4b` quantised to Q4), with three EARS requirements generated,
six lint rules executed, and a 39-line vitest file emitted. Transcript
and generated test land in `docs/private/fixtures/` (gitignored).

## What the LLM does NOT do

- Invent inputs that aren't in the node list (e.g., no "Sign up" link
  unless one is present)
- Decide *what* the validation rule should be (e.g., the model says
  "invalid credentials" because the design names that error; it does not
  prescribe password length)
- Cross-reference design tokens or component libraries — that's M3+ scope
  once `library_content:read` is added to the token

## Performance

On a consumer laptop CPU:

- Cold start (model load): 5–15 s
- Per-call generation: 20–40 s for 8–10 nodes
- Memory: ~4 GB RAM for `gemma3:4b` Q4 quantisation

Switch to a smaller model (`gemma3:2b`) or a GPU-equipped machine for
faster iteration during M4/M5 development.
